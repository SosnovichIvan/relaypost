# Миграция и backfill

Раздели изменение на расширение схемы, совместимый код, перенос данных,
проверку и удаление старой структуры, если приложение обновляется постепенно.
Для одноразовой локальной БД не навязывай этот процесс без необходимости.

До DDL проверь существующие NULL/duplicates/orphans и требования старых writers.
Определи, берёт ли операция lock, переписывает ли таблицу, допускается ли внутри
транзакции и как отменяется в версии целевого движка. Имя online не означает
отсутствия блокировок или нагрузки.

Backfill должен иметь устойчивый cursor, ограниченный batch, условие повторного
запуска и метрику завершения. Определи, как concurrent writes не теряются и не
перезаписываются старым значением; OFFSET по меняющимся данным может пропускать
строки. Не выполняй длительный backfill одной транзакцией по умолчанию.

Перед cutover сравни полноту и бизнес-инварианты, а не только число строк.
Удаляй старые поля после прекращения их использования всеми поддерживаемыми
версиями. Укажи точку, после которой возврат старого приложения невозможен.

Recovery может быть forward fix или восстановлением в отдельную среду. DROP
нового поля в down migration не возвращает удалённые старые данные. Для
разрушительного изменения планируй сохранение данных и проверку восстановления
по требованиям проекта; не обещай универсальный rollback.
