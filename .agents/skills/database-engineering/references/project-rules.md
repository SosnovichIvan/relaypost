# Правила: database-engineering

Применяются при подключённом профиле `--project-rules standard` или явном
выборе владельца. Обязательные требования владельца не выдаются за стандарт
внешнего источника. Для существующего несовместимого проекта обозначь конфликт,
не меняй архитектуру без задачи на переход.

## Обоснование схемы

На каждую таблицу до реализации заполни: сценарий, владелец, идентификатор,
кардинальности связей, nullability, уникальность, политика удаления, объём и рост.
Не создавай таблицу без потребителя. Ограничение целостности выражай в БД,
если оно должно сохраняться при конкурентных writers; SELECT перед INSERT
не заменяет UNIQUE. Укажи точность денег и семантику времени.

## Запрос и индекс

Сохрани исходный SQL с параметрами, ожидаемую частоту, размер результата,
распределение данных и текущие индексы. Для нового индекса объясни порядок
колонок через equality/range/order-by, селективность, цену записи и хранения.
Сравни план и измерение до/после на представительной среде; не требуй index scan
для маленькой таблицы, если последовательное чтение дешевле. Стоимость плана
не равна миллисекундам. Проверяй число loops/строк, сортировки и обращения к таблице.
Пагинация должна иметь устойчивый порядок; ограничь размер выборки.

## Миграция до PR

Запиши версию движка, исходную/целевую схему, порядок deploy и блокировки.
Для несовместимого изменения применяй этапы: добавить совместимую структуру,
перевести запись, выполнить ограниченный возобновляемый backfill, проверить
данные, переключить чтение, удалить старое отдельным шагом после ухода старых клиентов.
Не редактируй применённую миграцию. Backfill имеет checkpoint, размер batch,
контроль нагрузки, повтор и проверку полноты. Укажи восстановление после частичного
сбоя; для потери данных down-скрипт не заменяет проверенное восстановление.

Проверь пустую БД и обновление предыдущей схемы с данными, ограничения,
параллельную запись, старого/нового клиента, отказ между шагами и повтор backfill.
Отчёт до PR: SQL/план до-после, объём тестовых данных, длительность, блокировки,
совместимость и recovery. Без эксперимента пометь оценку как непроверенную.
Реальная общая/production БД меняется только в рамках предоставленного разрешения.

## Покрытие

Для исполняемого кода мигратора/репозитория — порог владельца 90% строк и ветвей.
Процент SQL-схемы не выдумывай: DDL проверяется сценариями и инвариантами на
целевой СУБД. Отсутствующее измерение не объявляй прохождением порога.
