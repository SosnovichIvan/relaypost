# Database engineering

Подготовь проверяемое изменение данных с понятным порядком применения.
Skill устанавливается независимо; migration tool и ORM бери из проекта.

## До изменения

Определи СУБД и версию, схему, migration history, объём/распределение данных,
конкурентные writers, роль подключения и среду. Не угадывай production по имени
переменной. Для локального изменения файлов подключение к production не нужно.
Если данных о нагрузке нет, назови предположения и не обещай zero downtime.

## Реализация

- Начни с инварианта: ownership/tenant, nullability, uniqueness, foreign keys,
  допустимые переходы и поведение удаления. Вырази его constraint там, где
  это соответствует модели. Предварительная SELECT-проверка не защищает от race.
- Выбери транзакционную границу по инварианту. Учитывай isolation, порядок
  блокировок, conflict/retry и атомарные conditional updates.
- Параметризуй значения; идентификаторы выбирай из allowlist. Не считай ORM
  гарантией безопасности raw SQL, tenant scope или отсутствия N+1.
- Индекс обоснуй запросами, селективностью, сортировкой и ценой записи/хранения.
  Проверь существующие индексы до добавления нового.
- Не редактируй уже применённую миграцию, если политика проекта не допускает
  пересоздание среды; добавь следующую. Сохраняй стабильный порядок миграций.
- Для денежных/временных значений сохрани требуемые precision, timezone и
  семантику округления. Не меняй тип только ради удобства языка приложения.

## Проверка и применение

Проверь миграцию на пустой и заполненной тестовой БД целевого движка; для риска
проверь старого и нового клиента, повторы и конкурентные writes. SQLite не
доказывает корректность блокировок PostgreSQL/MySQL.

Разделяй готовые файлы, тестовое применение и применение к общей/production БД.
Используй уже выданное разрешение; если реальное изменение не входит в него,
сначала подготовь SQL, целевую среду, ожидаемые эффекты, verification и recovery,
затем запроси разрешение именно на применение. Не требуй подтверждения для
каждой локальной правки или разрешённого теста.

Отдай изменённый инвариант, файлы, порядок rollout, проверки и recovery plan.
Укажи, где команды реально запускались. Не выдавай написанный SQL за применённую
миграцию, backup — за проверенное восстановление, а estimate — за измерение.

## Профиль правил проекта

Применяй [профильные правила](references/project-rules.md) только при явном согласии
на правила этого скилла в инструкциях проекта. При наличии approved snapshot
используй его; наличие файла само по себе не активирует правила. Они не запускают другие скиллы автоматически.
