# Project architecture

Преврати требования в минимальную реализуемую систему и объясни компромиссы.
Skill самодостаточен, не запускает implementation skills и не создаёт
инфраструктуру автоматически. Не подменяй архитектуру деревом директорий.

## Основания решения

Для существующего проекта восстанови фактические границы по entrypoints,
зависимостям, схемам данных и deployment. Отличай реализованное от документации.
Для нового проекта определи основные сценарии, владельцев, ограничения команды,
бюджет, data lifecycle и допустимый operational overhead.

Зафиксируй измеримые требования там, где они известны: нагрузка и её пики,
latency, доступность, восстановление, консистентность, объём/рост данных.
Не выдумывай цифры. Неизвестное помечай предположением с последствием и способом
проверки; спрашивай только то, что существенно меняет решение, продолжая остальную работу.

## Проектирование

1. Определи бизнес-инварианты и владельца каждого набора данных. Назови
   разрешённые зависимости между модулями и публичные контракты.
2. Для существенного выбора сравни реалистичные альтернативы, включая
   сохранение текущей системы. Учитывай сложность разработки, эксплуатации,
   стоимость перехода и обратимость; не делай микросервисы стартовым ответом.
3. Проследи ключевой сценарий и отказ: клиент → вход → решение → данные →
   внешний эффект. Отметь trust boundaries, authorization, transaction boundary,
   retries, ownership фоновой работы и наблюдаемость там, где они нужны.
4. Выбери достаточно подробную схему: context/containers обычно объясняют
   систему; component/deployment/sequence добавляй для конкретного вопроса.
   На стрелках укажи смысл/протокол, отдели процесс от модуля внутри процесса.
5. Для изменения действующей системы опиши совместимость, этапы rollout,
   миграцию данных, cutover, recovery и условия удаления старого пути.

Для решения с долгосрочными последствиями прочитай
[decision-record.md](references/decision-record.md). Для небольшой задачи
достаточно короткого решения в существующем документе проекта.

## Проверка и передача

Пройди по сценариям и убедись, что у данных, ошибок, background tasks и
контрактов есть владелец. Проверь циклы зависимостей и несовместимые гарантии:
например, нельзя одновременно обещать мгновенный внешний эффект и его откат
локальной DB-транзакцией. Не заявляй capacity/availability без соответствующих
измерений или расчёта с явными исходными допущениями.

Результат: решение и причины, схема, контракты и инварианты, этапы реализации,
проверки приёмки и нерешённые вопросы. Отмечай статус proposed/accepted согласно
реальному решению пользователя; не объявляй предложение согласованным сам.
Артефакты должны позволять начать реализацию без повторного изобретения границ.

Схемы уточняй по [C4 model](https://c4model.com/diagrams), если эта нотация
помогает задаче; не требуй все уровни C4 для каждого проекта.

## Профиль правил проекта

Применяй [профильные правила](references/project-rules.md) только при явном согласии
на правила этого скилла в инструкциях проекта. При наличии approved snapshot
используй его; наличие файла само по себе не активирует правила. Они не запускают другие скиллы автоматически.
