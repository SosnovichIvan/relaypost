# Правила: project-architecture

Применяются при подключённом профиле `--project-rules standard` или явном
выборе владельца. Обязательные требования владельца не выдаются за стандарт
внешнего источника. Для существующего несовместимого проекта обозначь конфликт,
не меняй архитектуру без задачи на переход.

## Решение об архитектуре

Запиши сценарии, ограничения нагрузки/latency, чувствительные данные, владельцев
и эксплуатационные возможности. Определи независимые модули по бизнес-ответственности,
а не по таблицам или контроллерам. Для каждого укажи публичный контракт, данные,
зависимости, транзакции и способ изолированного тестирования.

Frontend будущего проекта использует FSD: разделяй страницы, действия, сущности
и инфраструктуру, проверяй зависимости сверху вниз. Backend выбирается по стеку
и сложности: модульный монолит подходит, пока независимое развёртывание не обосновано.
Для отдельного сервиса обоснуй пользу относительно сетевых отказов, согласованности,
мониторинга и стоимости. Не делай общую БД неявным API независимых сервисов.

ADR содержит контекст, варианты, принятое решение, последствия, схему зависимостей,
план перехода и критерий пересмотра. Повторяемую логику вынеси в общий модуль только
с определённым владельцем; не превращай shared в зависимость всех от всех.

До реализации назначь проверяемые контракты и coverage 90% строк/ветвей по каждому
сервису. Для БД заложи upgrade/backfill/совместимость, для доставки — PR через develop
в main и выпуск по тегу. Проверка архитектуры: граф без циклов, изолируемые тесты,
явные ownership и отказные сценарии. Диаграмма без контрактов не подтверждает границы.

Источник выбора границ: [Microsoft application architectures](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures), проверен 2026-09-14.
