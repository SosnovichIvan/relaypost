# Контракты и отказоустойчивые изменения

Читайте для API evolution, queue/worker, webhook, cache или retry.

Для API изменения проверь старого consumer во время rollout: optional/required
fields, enum expansion, defaults, error mapping и pagination. Совместимость
проверяется на observable wire contract, а не только на компиляции сервиса.

Для идемпотентной команды определи scope ключа, fingerprint запроса, concurrent
claim, in-progress/completed и replay. Уникальный ключ без проверки владельца
или тела может вернуть чужой/неподходящий результат. TTL должен соответствовать
окну повторов продукта; не назначай произвольное значение как универсальное.

Для внешнего эффекта рассмотрите остановку до/после вызова и записи результата.
DB-транзакция не отменяет уже отправленный HTTP/email. Если инвариант требует
durable intent, используй существующий outbox/queue механизм; consumer должен
выдерживать redelivery. Не добавляй брокер без нужной гарантии.

Webhook проверяет аутентичность по контракту провайдера и его исходным bytes,
обрабатывает повторы и порядок событий. Не доверяй timestamp/status только
потому, что JSON проходит schema validation.

Retry ограничен общим deadline и классификацией ошибок. Timeout не доказывает
отсутствие эффекта; не повторяй неидемпотентную операцию без reconciliation.
Для cache укажи owner, key scope, invalidation и допустимую stale policy;
не используй кеш как единственный источник бизнес-инварианта.

Проверки должны включать конкретный сбой или повтор, ради которого добавлена
логика. Передай контракты, rollout и оставшиеся неопределённости следующему
шагу без автоматического вызова соседнего skill.
