# Backend service architecture

Читайте эту справку при выборе package boundary, dependency direction,
контракта или обработки ошибок.

## Границы

Названия директорий подстрой под проект, сохраняя обязанности:

```text
cmd/config → transport → application/domain → repository or external client
```

- `cmd` только собирает зависимости, запускает процесс и завершает его;
- transport владеет HTTP/gRPC/message parsing, protocol validation и mapping;
- application/domain владеет use cases и бизнес-инвариантами;
- repository/client инкапсулирует БД и внешние системы;
- contract/generated packages не содержат бизнес-решений.

Зависимости направлены внутрь. Не позволяй handler обращаться к БД напрямую или
domain зависеть от HTTP/gRPC типов. Абстракцию размещай на подтверждённой
архитектурной границе; не создавай её без альтернативного поведения, test seam
или необходимости разорвать зависимость.

## Контракты

Определи канонический источник: OpenAPI, protobuf, GraphQL schema, AsyncAPI или
внутренний программный API. Изменение начинается там только если реально меняется
контракт. Выполни штатную генерацию и проверь clean regeneration diff.

Backward-incompatible изменение требует явной версии/миграции потребителей.
Не дублируй одну wire model вручную в нескольких слоях; domain model может быть
отдельной, если отделяет протокол от бизнес-логики.

## Ошибки и lifecycle

- Добавляй контекст без потери исходной причины средствами выбранного языка.
- Стабильные domain errors отображаются в transport codes в одном месте.
- Логируй ошибку на границе, которая принимает решение, а не на каждом уровне.
- Конструктор проверяет обязательные зависимости; startup возвращает ясную
  ошибку до начала обслуживания запросов.
- Shutdown прекращает приём новых запросов, отменяет workers и ограничен
  deadline.
