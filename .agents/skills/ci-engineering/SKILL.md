# CI engineering

Собери воспроизводимые проверки PR по реальному составу проекта, а не по
фиксированному шаблону frontend/backend. Skill самодостаточен, не запускает
другие skills и не выдаёт права менять remote protection или production.

## Сначала состав проекта

Прочитай agent instructions, manifests/lockfiles, команды тестов, CI и runtime
entrypoints. Найди приложения, библиотеки, worker/cron/bot/CLI, БД, очередь,
cache, gateway и deployment-конфигурацию. Отдели собственный код от внешних
зависимостей: не добавляй тесты внутренностей Redis только из-за его наличия.

До YAML составь матрицу по
[quality-contract.md](references/quality-contract.md): компонент → реальные
команды → тестовые зависимости → измерения → CI job → обязательный gate.
У отсутствующей проверки укажи `gap`, у неприменимой — `N/A` с причиной.
Не превращай `gap` в зелёный job с `echo`, нулём тестов или `continue-on-error`.

## Реализация

Используй существующий CI provider, package manager и тестовый стек. Проверь
доступность каждой команды и поддержку flags в закреплённой версии. Не заменяй
Cypress на Playwright или наоборот без задачи на смену стека. Для GitHub Actions
прочитай [github-actions.md](references/github-actions.md) перед изменением workflow.

Для frontend и bot-интеграций явно проверь обязательность соответствующих
E2E/integration gates по действующей policy: наличие jobs недостаточно.
При bot-интеграции или связи UI с ботом прочитай
[bot-integration.md](references/bot-integration.md). Не объявляй браузерный
`intercept` доказательством работы backend/worker/доставки.

Начни с запуска всех применимых наборов на каждом PR. Оптимизацию по путям
добавляй только с проверяемым графом влияния: shared-код, lockfiles, конфигурация,
генератор и CI затрагивают потребителей. Новый/неизвестный путь не должен
автоматически считаться безопасным. Сохраняй стабильный обязательный итоговый
gate, если jobs могут пропускаться; ошибка определения scope — failure.

Соблюдай действующую coverage policy отдельно для каждого приложения/сервиса.
Не придумывай branch coverage из statements, не усредняй разные сервисы и не
объявляй отсутствующий отчёт успешным. Нулевая база — N/A, а не 100%.
Если порог не задан, предложи его явно; не выдавай личное предпочтение за стандарт.

Проверки работают в изолированных средах, с фиктивными данными и без реальных
сообщений/платежей. PR не публикует релиз, не выполняет production migration и
не использует production secrets. Verification build допустим по политике проекта.

## Проверка и передача

Проверь синтаксис provider-specific validator, реальные команды и артефакты.
Сценарии: успешный набор; failing test; провал coverage; ошибка зависимости;
провал/отмена/skipped нужного job; изменение shared/lockfile/CI; новый сервис;
docs-only PR. Для conditional DAG отдельно проверь, что итоговый gate не
становится success при неполной проверке. Не создавай сломанный PR или внешнюю
нагрузку для эксперимента без разрешения; локальная проверка не доказывает
работу удалённого runner.

При настройке PR gates включай фактическую защиту целевых веток в результат
работы: сверь точные имена и источник checks, сохрани действующие ограничения,
примени protection в рамках разрешения на указанный репозиторий и перечитай
remote state после записи. Синхронизируй хранимую конфигурацию защиты.
Файл с protection не доказывает её применение. Без необходимых прав или
разрешения запроси их и обозначь незавершённый enforcement; skill сам по себе
прав не даёт. Не отключай проверки ради исключения владельца по ревью.
Отчёт: матрица,
изменённые файлы, команды/версии/результаты, local vs CI, список gaps и статус
enforcement (`configured`, `verified` или `not_verified` с основанием).
