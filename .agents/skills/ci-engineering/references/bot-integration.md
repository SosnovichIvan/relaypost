# Bot-интеграции в PR-проверках

Читай для Telegram/Discord/Slack и других реализованных bot adapters, включая
Mini App или UI, запускающий действия бота. Не навязывай всем платформам
Telegram Update, webhook или outbox: восстанови реальный entrypoint проекта.

## Два разных доказательства

Browser E2E подтверждает пользовательский сценарий в UI. Contract/integration
suite бота подтверждает принятие событий, права, persistence и внешний эффект.
Если UI связан с ботом, хотя бы один критический путь запускается через реальный
тестовый backend и его transport adapter до контролируемого endpoint/stub;
`cy.intercept`/эквивалент, возвращающий готовый успех API, для него недостаточен.
Код framework (aiogram и аналогичный) сам по себе не является объектом coverage.

## Что запускать

1. Подними изолированный backend и используемые им БД/очередь, дождись readiness.
   Создай синтетические identity, роли и chat membership штатными fixture.
2. Подай событие через настоящий dispatcher/router. Для webhook проверь
   аутентификацию/подпись, если они используются. Для polling не запускай
   конкурирующий production poller; synthetic updates подаются в test harness.
3. Проверь пользователя и объект: разрешённое действие, отказ чужому пользователю,
   неизвестные/невалидные входы; не доверяй подставленной UI роли.
4. Если сценарий хранит событие или ответ, проверь записи целевой тестовой БД,
   очередь и worker через настоящие application paths. Если stateless — N/A
   для persistence с причиной. Повтор update не должен повторять эффект там,
   где контракт обещает идемпотентность.
5. Перехвати исходящий transport запрос после adapter и проверь адресата,
   существенный payload и обработку ответа. Протокольный stub должен различать
   success, rejection, rate limit и timeout там, где это есть в контракте.
   Проверь retry budget и неоднозначную доставку, не обещая exactly-once
   при неизвестном исходе сети.
6. Для связанного UI проверь реальный результат действия: сохранённые данные
   и наблюдаемый исходящий запрос, а не только текст toast. SDK платформы и
   initData заменяй тестовым adapter/подписью исключительно в тестовой среде;
   production authorization не отключай.

## Gate и границы

При approved delivery policy bot suite обязательна даже без frontend. Связь
со стабильным required gate проверяется отдельно от успешного запуска suite.
Нужный job failed/cancelled/skipped → merge не разрешён; группировка в общий
Backend job допустима, если там действительно запускаются эти тесты.

Test token должен быть фиктивным, получатели — синтетическими, внешние запросы
идут только в контролируемый stub. Закрой случайный outbound к живой платформе
средствами harness/runner и проверь ошибку при попытке его обойти. Не используй
production secrets даже для fork PR из собственного аккаунта. Cleanup не
затрагивает общую БД. Ручная приёмка живого клиента/SDK/доставки остаётся отдельной
разрешённой проверкой; локальный stub не доказывает доступность платформы.
