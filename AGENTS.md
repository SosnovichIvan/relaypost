# Правила: project-architecture

Применяются при подключённом профиле `--project-rules standard` или явном
выборе владельца. Обязательные требования владельца не выдаются за стандарт
внешнего источника. Для существующего несовместимого проекта обозначь конфликт,
не меняй архитектуру без задачи на переход.

## Решение об архитектуре

Запиши сценарии, ограничения нагрузки/latency, чувствительные данные, владельцев
и эксплуатационные возможности. Определи независимые модули по бизнес-ответственности,
а не по таблицам или контроллерам. Для каждого укажи публичный контракт, данные,
зависимости, транзакции и способ изолированного тестирования.

Frontend будущего проекта использует FSD: разделяй страницы, действия, сущности
и инфраструктуру, проверяй зависимости сверху вниз. Backend выбирается по стеку
и сложности: модульный монолит подходит, пока независимое развёртывание не обосновано.
Для отдельного сервиса обоснуй пользу относительно сетевых отказов, согласованности,
мониторинга и стоимости. Не делай общую БД неявным API независимых сервисов.

ADR содержит контекст, варианты, принятое решение, последствия, схему зависимостей,
план перехода и критерий пересмотра. Повторяемую логику вынеси в общий модуль только
с определённым владельцем; не превращай shared в зависимость всех от всех.

До реализации назначь проверяемые контракты и coverage 90% строк/ветвей по каждому
сервису. Для БД заложи upgrade/backfill/совместимость, для доставки — PR через develop
в main и выпуск по тегу. Проверка архитектуры: граф без циклов, изолируемые тесты,
явные ownership и отказные сценарии. Диаграмма без контрактов не подтверждает границы.

Источник выбора границ: [Microsoft application architectures](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures), проверен 2026-09-14.

### Approved rule: backend-engineering

Source: `skills/backend-engineering/references/project-rules.md`

# Правила: backend-engineering

Применяются при подключённом профиле `--project-rules standard` или явном
выборе владельца. Обязательные требования владельца не выдаются за стандарт
внешнего источника. Для существующего несовместимого проекта обозначь конфликт,
не меняй архитектуру без задачи на переход.

## Архитектура реализации

До кода запиши входной контракт, инвариант, владельца данных, транзакционную
границу и способ проверки. Выбирай архитектуру по сложности домена и стеку,
а не автоматически «микросервисы». HTTP/queue adapter преобразует вход;
application service выполняет сценарий; доменная логика хранит инвариант;
инфраструктура реализует доступ к внешним ресурсам. Не добавляй пустые слои.

Модуль имеет публичный контракт, закрытые детали, явные зависимости и изолированные
тесты. Запрещены циклы и чтение внутренних таблиц другого сервиса в обход владельца.
Общий модуль извлекай при повторном использовании одного поведения. Не делай
бизнес-модули зависимыми от глобального контейнера ради удобства теста.
Для сетевого взаимодействия укажи timeout, cancellation, retry budget,
идемпотентность и поведение частичного отказа. Повтор без ключа идемпотентности
не должен дважды создавать оплату/тренировку/заказ.

## Контракты и данные

Валидируй вход на границе; проверяй права на действие и конкретный объект.
Параметризуй SQL; ORM не заменяет tenant scope и анализ запросов. До PR
для каждого изменённого пути перечисли запросы, N+1, границы выборки, индексы,
транзакции и миграции. Если данных/схемы нет, запиши основание N/A.
Не держи транзакцию во время неограниченного сетевого вызова. Согласуй порядок
commit и отправки события; при необходимости используй outbox с повторной обработкой.

## Проверка сервиса

Проверь успешный контракт, неправильные данные, запрет доступа, повтор,
таймаут и rollback. Интеграционные тесты используют целевой движок БД.
Контрактный тест ловит несовместимость потребителя, а unit-тест домена не требует
работающего HTTP-сервера. Вывод отчёта: контракт, изменения данных, доказательства,
известные ограничения. Сценарии риска выбирай по фактическому изменению.

## Проверка тестами

Требование владельца: минимум 90% строк и ветвей исполняемого авторского кода
по затронутому приложению/независимому сервису; также по изменённому коду при
достоверной поддержке diff coverage. Не усредняй frontend и backend.
Измеряй и неисполненные файлы, а не только импортированные тестами. Исключения:
generated/vendor и неисполняемые декларации, по явному списку. Отсутствующий
отчёт — блокирующая непроверенность, нулевой знаменатель — N/A, не 100%.
CI обязан отклонять результат ниже порога. Если инструмент измеряет только
statements (например, стандартный Go coverage), не называй их branches/lines:
зафиксируй метрику и согласуй дополнительную проверку до заявления о прохождении.
Не понижай порог и не исключай сложную логику. Порог — политика проекта,
а не гарантия отсутствия ошибок и не требование внешней документации.
В отчёте укажи команду, версию инструмента, область, exclusions, проценты
и непроверенные сценарии. Тесты должны проверять поведение и значимые ошибки.

### Approved rule: database-engineering

Source: `skills/database-engineering/references/project-rules.md`

# Правила: database-engineering

Применяются при подключённом профиле `--project-rules standard` или явном
выборе владельца. Обязательные требования владельца не выдаются за стандарт
внешнего источника. Для существующего несовместимого проекта обозначь конфликт,
не меняй архитектуру без задачи на переход.

## Обоснование схемы

На каждую таблицу до реализации заполни: сценарий, владелец, идентификатор,
кардинальности связей, nullability, уникальность, политика удаления, объём и рост.
Не создавай таблицу без потребителя. Ограничение целостности выражай в БД,
если оно должно сохраняться при конкурентных writers; SELECT перед INSERT
не заменяет UNIQUE. Укажи точность денег и семантику времени.

## Запрос и индекс

Сохрани исходный SQL с параметрами, ожидаемую частоту, размер результата,
распределение данных и текущие индексы. Для нового индекса объясни порядок
колонок через equality/range/order-by, селективность, цену записи и хранения.
Сравни план и измерение до/после на представительной среде; не требуй index scan
для маленькой таблицы, если последовательное чтение дешевле. Стоимость плана
не равна миллисекундам. Проверяй число loops/строк, сортировки и обращения к таблице.
Пагинация должна иметь устойчивый порядок; ограничь размер выборки.

## Миграция до PR

Запиши версию движка, исходную/целевую схему, порядок deploy и блокировки.
Для несовместимого изменения применяй этапы: добавить совместимую структуру,
перевести запись, выполнить ограниченный возобновляемый backfill, проверить
данные, переключить чтение, удалить старое отдельным шагом после ухода старых клиентов.
Не редактируй применённую миграцию. Backfill имеет checkpoint, размер batch,
контроль нагрузки, повтор и проверку полноты. Укажи восстановление после частичного
сбоя; для потери данных down-скрипт не заменяет проверенное восстановление.

Проверь пустую БД и обновление предыдущей схемы с данными, ограничения,
параллельную запись, старого/нового клиента, отказ между шагами и повтор backfill.
Отчёт до PR: SQL/план до-после, объём тестовых данных, длительность, блокировки,
совместимость и recovery. Без эксперимента пометь оценку как непроверенную.
Реальная общая/production БД меняется только в рамках предоставленного разрешения.

## Покрытие

Для исполняемого кода мигратора/репозитория — порог владельца 90% строк и ветвей.
Процент SQL-схемы не выдумывай: DDL проверяется сценариями и инвариантами на
целевой СУБД. Отсутствующее измерение не объявляй прохождением порога.

# Политика Git и релизов

Требования владельца будущих проектов; не профиль frontend или БД.

## Git, PR и выпуск

- Разработка ведётся в отдельных рабочих ветках. Любые прямые push, включая
  force push, в `develop` и `main` запрещены для людей, агентов и ботов.
- Из рабочей ветки PR создаётся только в `develop`. В `main` допускается только
  PR из `develop`. Hotfix проходит тот же путь. Изменения защищённых веток
  доставляются только слиянием PR через платформу после обязательных проверок.
- Настрой защиту обеих веток: обязательный PR, успешные проверки, ревью,
  запрет force push и удаления, отсутствие обхода для администратора и ботов.
  Проверка PR должна отклонять любое другое сочетание исходной и целевой веток.
- Релизная сборка, публикация пакета/контейнера и deployment запускаются только
  после создания версионного тега на коммите, входящем в историю `main`.
  Проверяй принадлежность коммита актуальной удалённой `main` до сборки.
  Один лишь шаблон имени тега не доказывает принадлежность `main`.
- Тег имеет формат `MAJOR.MINOR.PATCH` (например, `1.0.1`), неизменяем и не
  переносится. Ошибка исправляется новым коммитом и новым тегом.
- На PR запускаются lint, проверка типов, тесты, coverage и анализ миграций.
  Компиляция исключительно для этих проверок допустима, без выпуска релизного
  артефакта. На push ветки или ручной запуск без проверенного тега релиз не идёт.
  Это разграничение позволяет проверять код до слияния, сохраняя выпуск по тегу.


## Обязательная полнота PR-проверок

На старте проекта и при добавлении/удалении приложения, сервиса или runtime-
зависимости веди матрицу: компонент/root → команды проверок → тестовые службы
и версии → coverage policy → CI check → required gate. Включай API, worker,
bot/cron/CLI, UI, общие библиотеки и infrastructure, если они есть. Группировка
в одном job допустима при доказуемом охвате всех компонентов. Для неприменимого
набора укажи N/A с причиной; для отсутствующего — gap, не success.

Каждый PR запускает применимые format/lint/static/types, unit/integration,
contract и критические E2E-проверки по реальному стеку. Не навязывай отсутствующие
БД, браузер или тестовый framework. БД и другие службы поднимай изолированно с
healthcheck, ограниченным timeout и фиктивными данными; интеграционные гарантии
целевой СУБД проверяй на ней, не на mock/другом движке. Для схемы проверяй пустой
upgrade, обновление предыдущей схемы с данными и drift; downgrade — только если
поддерживается контрактом проекта, никогда в общей/production БД.

Coverage проверяется отдельно по каждому авторскому приложению/независимому
сервису: минимум 90% строк и ветвей с включением неимпортированных исполняемых
файлов. Exclusions — явные generated/vendor/неисполняемые декларации, не сложная
логика. Отсутствующий отчёт — блокирующая непроверенность, нулевой знаменатель —
N/A. Statements не выдавай за branches; если инструмент не измеряет метрику,
зафиксируй gap и согласуй способ проверки, не объявляй порог пройденным.
DDL и документация проверяются инвариантами/валидаторами, не выдуманным процентом.
Порог — требование владельца, не стандарт платформы CI.

### Frontend и интеграции с ботами — обязательные gates

Если есть web frontend, браузерные E2E критических пользовательских сценариев
обязательны, а не факультативны. Для нового web-проекта используй Cypress;
если в существующем проекте уже есть другой E2E framework, сохраняй его gate,
а замену согласуй отдельно. Для native frontend нужен соответствующий UI/E2E
harness, не браузерный инструмент без web-поверхности. Отсутствие harness — gap,
не основание объявить E2E N/A. Cypress job должен входить в required checks
либо в проверенный обязательный aggregate gate, когда используется Cypress.

Если есть интеграция с ботом, обязательны contract/integration tests: входящее
событие → реальный dispatcher/application service → тестовое хранилище/очередь
(если используются) → исходящий запрос к контролируемому transport stub.
Проверь права, повтор входящего события и значимые отказы доставки; применяй
только существующие в интеграции механизмы. При связи frontend с ботом нужен
хотя бы один сквозной тест через реальный тестовый backend, а не только
`intercept` браузера. Browser E2E, тесты bot adapter и coverage не заменяют
друг друга. Нет UI, но есть bot — bot integration gate всё равно обязателен.

Оба применимых набора должны блокировать merge при провале. Наличие job без
связи с required checks недостаточно. PR использует синтетических пользователей,
локальный/fake API и тестовую БД; реальные bot tokens и пользователи не нужны.
Живую проверку платформы выполняй отдельно только с разрешением. Неподключённая
будущая интеграция записывается planned/N/A с причиной, а не как пройденный тест.

Сначала запускай все применимые наборы на каждом PR. Выборочное выполнение
допустимо с проверяемой картой зависимостей: shared, lockfiles, contracts,
toolchain и CI затрагивают всех потребителей; неизвестный путь вызывает полный
набор либо блокировку. При conditional jobs обязателен стабильный итоговый gate,
который отклоняет failed/cancelled/неожиданно skipped jobs и ошибку detector.
Docs-only PR тоже получает завершённый required gate по явной policy. Проверяй
положительный и отрицательный пути, не только валидность YAML.

Настрой соответствие обязательных checks фактической защите целевых веток:
наличие workflow или JSON-файла protection не означает, что merge заблокирован.
Настройка защиты веток входит в результат задачи настройки PR-проверок, а не
остаётся необязательным следующим шагом. После разрешённого изменения remote
перечитай protection/rulesets и проверь required checks всех целевых веток,
обязательный PR, запрет force push/удаления и действующие reviewer exceptions.
Сохраняй более строгие существующие ограничения; исключение владельца по ревью
не должно отключать проверки. Обнови хранимую конфигурацию защиты в проекте.
При добавлении gate сначала убедись, что check с таким именем и доверенным
источником существует, чтобы не заблокировать merge несуществующим статусом.
Без доступа/разрешения запроси необходимое и пометь enforcement как
`not_verified`: это незавершённая часть поставки, не успешно настроенная защита.
Не распространяй разрешение для одного репозитория на другие проекты.
Не скрывай failure через continue-on-error,
пустые тесты, понижение порога или исключение проблемного компонента.

PR-код недоверенен: минимальные permissions, без production secrets, реальных
рассылок, publish, deploy и migration общей БД. Проверки конфигурации и
verification build не являются релизом. Отчёт содержит commands/versions,
статусы компонентов, coverage отдельно, CI/local evidence и оставшиеся gaps.

Проверка настройки: попытка прямого push отклоняется; PR feature → main отклоняется;
PR feature → develop и develop → main допускается после проверок; тег вне main
не выпускает артефакт. Проверять без публикации пробных production-релизов.

Источник механизма защиты, проверен 2026-09-14: [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
Требование именно develop → main и выпуск по тегу — политика владельца, не стандарт GitHub.
